# Take Home Summary

This repo deploys a Premium Azure Container Registry and supporting network components in West Europe, deployed with Terraform
and Terragrunt. It is private-only, zone-redundant, geo-replicated, audited
and protected against deletion.

Human administration and CI/CD are separated: Azure Bastion provides
controlled access to private management resources, the environment is capable of hosting a self-hosted GitHub runner inside the VNet 
for private registry access. 




1. SECURITY

* Public network access disabled on the registry; ACR is accessed through a Private Endpoint
  and private DNS.
* ACR admin user is disabled and anonymous pull is blocked; access uses Entra ID and RBAC.
* Azure Policy assignments deny public access, admin-user use, anonymous pull, and export operations.
* AcrPush/AcrPull granted only to explicitly configured principals.
* Export policy disabled.
* AzureServices bypass supports server-side Azure operations such as
  `az acr import`.
* Terraform Remote state is configured to use Entra authentication rather than storage keys.
* GitHub Actions authenticates to Azure through GitHub OIDC (`azure/login@v2`) instead of a long-lived client secret.
* The VM bootstraps with no registry login requirement and does not expose service-principal credentials in cloud-init logs.
* OIDC is the only registry identity used by the workflow; the VM itself is not granted registry write access for the private CI path.
* The self-hosted runner and pipeline are designed to run inside the private network, while only short-lived identity tokens are used instead of static client secrets.
* Local validation environments such as `.venv/` are intentionally excluded from source control; only the repo validation scripts are versioned.
* Egress is limited to 443 by NSG policy. Production would add Azure Firewall with an allowlist for GitHub Actions and the standard Azure identity endpoints if tighter filtering is required.



2. RESILIENCE

* Zone redundancy enabled in West Europe and the North Europe replica for ACR.
* Geo-replication provides regional resilience and additional pull capacity.
* Deletion protected by both Terraform `prevent_destroy` and an Azure
  `CanNotDelete` management lock.
* The design includes a private management VM behind NAT and a dedicated Bastion path for administrative access.
* The environment supports ACR import and push workflows from a private runner inside the VNet.



3. NETWORK / ACCESS

* Dedicated subnet for the ACR Private Endpoint.
* Private management VM with no public IP and can only be reached through Bastion.
* Azure Bastion provides human SSH access to the private VM.
* Bastion is **not used for CI/CD**.
* The network is designed to keep registry traffic off the public internet.
* The self-hosted GitHub runner is supported through VM bootstrap.
* CI/CD will use a dedicated private runner with connectivity to the ACR
  Private Endpoint.



4. INFRASTRUCTURE AS CODE

* Reusable Terraform module with Terragrunt environment.
* Remote Azure Storage state with locking.
* Environment-specific values come from `prod.tfvars`; no environment
  CIDRs or names are hardcoded in resources.
* Terraform/provider versions are constrained and the provider lock file
  is committed.
* Input validation and consistent resource tagging are implemented.



5. PRIVATE CI / IMAGE PUSH FLOW

* The repository includes a GitHub workflow that runs from a self-hosted runner.
* The runner bootstrap is optional and controlled by Terraform variables rather than being hardcoded as a live deployment requirement.
* The environment is designed for private-network image delivery: the runner runs inside the VNet and uses Azure OIDC plus the VM's managed identity to access the registry over the private endpoint path.
* The smoke test invokes the ACR import flow (`az acr import`) instead of a raw Docker pull-and-push, which matches the intended private-registry ingestion pattern.
* A repo-level validation script checks that the example tfvars file remains parseable and region-consistent; this script is versioned, while the local `.venv` folder remains untracked.
* The successful workflow validates that the ACR private endpoint and access path are working for the supported import and repository validation flow.
* The design is aligned with a private-network CI pipeline model and is hardened with GitHub OIDC and managed identity instead of long-lived client secrets.
* The runner is treated as a dedicated build host for registry operations rather than as a general-purpose admin workstation.


6. AREAS TO COVER IF MORE TIME

* Continue with GitHub OIDC and managed identity over long-lived Azure credentials.
* Add image scanning, policy checks, signing, and approvals before production pushes.
* Rotate federated credentials and runner identities on a schedule, and keep VM identities scoped to the minimum required ACR permissions.
* Keep the runner isolated, patched, and limited to the required network paths.
* Add more alerting, audit logging, and operational monitoring around registry activity and runner access.
* Image scanning with tools like defender, trivy, snyk.
* Enforce github change management with branch protection, approval gates and CI only tf plan and apply
* Checkov/TFLint security and quality checks.
* CMK encryption if required by compliance.
